The spine — one line, no branches

This is the whole of what a shopper does. The feature lives at the product page and on the wishlist; everything else is Myntra's own app, rebuilt so the feature has somewhere real to sit. Buy Now is a parallel spine, not a step in this one: product page → Review Order → payment → confirmed, one garment, and the bag is never touched.

Opening the live prototype: Okay, Got it closes the sheet and returns to the page unchanged, the back arrow works on every screen that carries one, and a refresh resets the world to its seeded baseline — bag, wishlist and orders included. Nothing is written to storage, on purpose, so a refresh is the recovery move for anything at all. ?debug=1 prints the reasoning behind whichever answer you are looking at.

The product page is not one screen — it is seven answers

This is the part a linear diagram gets wrong. These are not steps after one another; they are the same node resolving differently on the data behind it — seven possible answers, and no eighth. In the prototype they are declared in lib/engine/types.ts.

Two things follow that are easy to miss. The invitation never appears in a list — on the wishlist a card with no verdict simply carries no line, and nothing marks the absence. And the answer changes with who is shopping, not just what is viewed: the profile is one control shared by both cards, so a kurta bought for someone else can never be compared against this shopper's jeans.

How Fabric Match works

Two layers, and the architectural point is when each of them runs. The prediction layer is a batch job over the catalogue — one pass per garment, its output stored as a fabric profile. The comparison layer is arithmetic against a single reference garment, cheap enough to run inside the product page's existing request budget. So the expensive half is paid once per SKU, not once per view. (The prediction layer is the half still to be built; the prototype on slide 9 stands in for it with authored values.)

the new work data and surfaces Myntra already has

What already exists

Roughly 60–70% of what Fabric Match needs is infrastructure Myntra runs today:

historyPurchase records, and which items were kept — the wardrobe is a view over them, not a new store
inferenceSub-2-second product-page inference, already serving size recommendations
captureThe studio photoshoot every SKU already goes through, and the seller portal that collects spec packs
UIThe block that renders the size card — the fabric line sits in the same one

What is new

Two things, and only the first is expensive:

the modelA computer-vision model pre-trained on fabric physics, predicting six tactile axes with per-axis confidence across the catalogue. This is the real cost, and it is a batch job — not a per-request one
the comparisonA layer that computes the difference between the viewed garment and one the shopper already owns, then writes it as a sentence. Arithmetic, essentially free
Myntra already predicts size from the same history and surfaces it as a verdict. Fabric Match adds an output to a stack that mostly exists — it does not build a new engine.

The vocabulary — six axes

The dimensions a shopper can actually feel, expressed as differences rather than specifications. Nothing here is a lab measurement: every value is a prediction about experience, and it carries the two qualifiers that keep it honest.

AxisUnitWhat the shopper hears
weightGSMheavier ↔ lighter
thicknessmmthicker ↔ thinner
stretch% recovery-adjustedstretchier ↔ more rigid
opacity0–100more opaque ↔ more sheer
structurebending indexstiffer ↔ softer, more fluid
surfaceordinaltextured ↔ smooth
Confidence — how far the available data actually constrains the value; below medium it is never spoken. Provenance — whether a value came from the catalogue, was predicted, or was inferred from reviews. Provenance is what lets the explainer sheet show its sources instead of asking to be trusted.

Shipping it is one widget

Myntra's product page is not a hand-laid template — it is an ordered list of server-driven widgets, verified from its own payload:

PDP_NATIVE_TOOLBAR ▸ ADD_BUTTONS ▸ IMAGE_SWIPE ▸ PDP_PRODUCT_INFO ▸ ADD_BUTTONS ▸ CONTENT_GROUPS ▸ [ FABRIC_AND_FEEL ] ▸ BRAND_QUALITY_INFO ▸ PRODUCT_RACK ▸ REVIEWS_QNA ▸ CROSS_LINKS ▸ MORE_INFO

The comparison line lives inside PDP_PRODUCT_INFO, where size selection already sits. The explainer sheet slots in as a new widget between CONTENT_GROUPS and BRAND_QUALITY_INFO. So the deployment is one widget added to an existing list — not a redesign, and not a new surface.

And it is allowed to say nothing. When fewer than two axes clear confidence on a garment, the feature renders nothing at all — no placeholder, no greyed row, no reserved gap. Abstention is a product rule, not an error path, which is why there is no empty state to design.
